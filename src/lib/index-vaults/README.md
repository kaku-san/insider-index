# Native index vault integration — full cycle (fail closed)

The September 14, 2026 revision-3 contract handoff selects **one existing Symmetry V3 vault and one native share mint per index**. This implementation does not deploy a program, mint a wrapper, custody assets in a service wallet, or maintain an ownership ledger. Investor actions require their own authorization; holders never sign native fund rebalances. Creation and naming belong only to the deployer.

## Full cycle contract

[`full-cycle.ts`](full-cycle.ts) owns create → zap-in → mint → keeper rebalance → USDC zap-out. Every stage is testable and **fails closed until that stage has a matching receipt**. Public Invest Sign stays off (`VAULT_RELEASE.publicInvestSign === false`) until then. Preview quotes are estimated, not guaranteed. Unused USDC is returned on the way in; exit is USDC only (host 25 bps in / 0 out). Vault legs are catalog tokens: xStock preferred, verified Backpack `.US` when there is no xStock, never invented DEX lookalikes (`vault-legs.ts`). Native `update_token_prices` remains Raydium-only; zap/eligibility quotes are Raydium first, Jupiter if no pool, never Pyth/Hermes. The SDK `isRebalanceRequired` helper is forbidden (it always opens Hermes). One vault per index, no default Pyth WSOL/USDC composition. Keeper is a dedicated hot wallet, not the deployer and not a Phantom click. Layout cap is 100 tokens; hundreds of names cannot be one vault — [`native-caps.ts`](native-caps.ts). Operator status: `npm run vault:cycle`.

## Current release boundary

The initial integration was read-only. A separately authorized devnet-only test created one vault and finalized a 0.1 SDK-USDC deposit that settled through the creation-time Pyth-type accounts; the vault's oracles were then switched to **Raydium CPMM only** and a second 0.1 SDK-USDC deposit completed deposit → lock → Raydium `update_prices` → mint → claim with zero Hermes/Pyth, using [`devnet-settle.ts`](devnet-settle.ts) (`npm run vault:settle:devnet`, [procedure](../../../docs/devnet-vault-settle.md)). Share supply is 199990. See [receipts and addresses](../../../evidence/vaults/DEVNET_TEST_VAULT.md). Person/index research surfaces do not mount its Invest preview. Preparation returns `503`/`wait` with no transactions because native readiness is still missing. A separate [native redemption preflight](../../../docs/devnet-vault-redeem.md) observes that vault and validates the SDK sell encoding, but always stops without signing or broadcast. No broadcast route exists. The separately managed contribution and lock are not performed or certified by this UI integration. Public funds, native-USDC exit, optional wallet conversion, automatic signing and native recovery actions remain disabled. There is no environment variable that silently enables them. The native settlement/share-transfer/redemption/fee roundtrip is **NOT_RUN**, not PASS. This is integration infrastructure, not a launch-ready or audited vault.

Legacy `/api/indexes/quote` and `/api/indexes/execute` return `503` without payloads/signatures. The old `STUBIDX`/in-memory index position writer is removed. Index pages display model allocations separately from unavailable actual native holdings. Existing single-trade Jupiter execution and full disclosed books remain separate and intact.

### Storage/recovery limits

Journals are private atomic JSON snapshots on **one durable local host**, fsynced and serialized by an exclusive directory lock. Place them under `.data/index-vaults/` (already ignored and outside the web root). They persist workflow observations, never signed spending payloads or secret bytes. Concurrent writers fail closed; a crashed `.lock` is **RECOVERY_REQUIRED**, not an automatically stolen lease. Inspect processes and prior signatures/state before deliberate lock recovery. No broadcast route exists while this recovery is manual.

Before distributed/unattended execution, replace the local journal with transactional shared storage, uniqueness constraints and fenced leases. Do not deploy these journals on ephemeral/serverless disks. Native state remains authoritative. Readiness/config changes invalidate preparation, not ownership. Old generations and outstanding claims must remain discoverable.

## SDK/source inspection

Pinned runtime dependencies: `@symmetry-hq/sdk@1.0.22`, `@solana/web3.js@1.98.4`, `@solana/spl-token@0.4.14`; exact npm integrity is in `package-lock.json` and `evidence/vaults/sdk-report.json`.

The SDK package identifies itself as **Symmetry V3** and is BUSL-1.1, with an Additional Use Grant explicitly permitting commercial Symmetry integration, not competing protocol/SDK infrastructure. No closed program source or SDK code is vendored. It ships typed binary layouts, **no standalone Anchor IDL JSON**. We record types/layout hashes, never relabel one as an IDL hash. This does not attest deployed binary/source correspondence.

Observed distributed-SDK details:

- Program constant (both networks): `BASKT7aKd8n7ibpUbwLP3Wiyxyi3yoiXsxBk4Hpumate`.
- Devnet SDK USDC is `USDCoctVLVnvTXBEuP9s8hntucdJokbo17RwHuNXemT`, not an assumed mainnet mint; no stock-route compatibility is inferred.
- `buyVaultTx` implementation emits **create + contribution** batches; its comment describes a lock batch which is commented out in this distribution. Use separate `lockDepositsTx` after confirmed creation/contribution, never assume the comment proves lock.
- Amount fields are raw integer **numbers**, not display units. SDK internals also convert some native counters/bounty balances with `parseInt`; large internal amounts need independent policy validation before any wallet release.
- `createVaultTx` derives addresses from the current native vault counter; persist returned vault and mint separately. Global-counter races and uncertain create receipts require reconciliation, not generation of a second vault.
- `updateTokenPricesTx` always constructs a Hermes client and requests Pyth price updates, even when the vault has zero Pyth oracles; the Raydium-only path builds `updateTokenPricesIx` directly instead. The instruction layout carries two fixed WSOL/USDC custody reference accounts as program constants; they are not vault oracles and are never updated here.
- Start-price builder parses a float then divides by `10^6`. The USD/USDC quote basis and bootstrap fairness remain unverified; **not enabled by a display label**.
- `sellVaultTx` has `keep_tokens`, no documented output-mint or aggregate minimum-USDC argument. Keep all allocated slots for baseline redemption; reconcile residuals and correct-program recipient ATAs before enabling claims.
- `signAndSend*`/SDK `simulateTransactions` helpers can send. Read-only connection middleware rejects non-read RPC methods, including send/airdrop. The scripts never load a signer.

`npm audit` currently reports transitive advisories (including bigint-buffer, axios, ws). The pinned SDK/SPL tree has no nonbreaking fix for every advisory; funds remain disabled. No blind audit-force downgrade or silent SDK upgrade was made. Review these before financial release.

## Person index mapping (top-20 FMP annual holdings)

The book is the **latest FMP annual holdings** (position-value midpoints) from the captain drop, committed verbatim (holdings not truncated) at `data/insiderindex-source-buckets/pelositracker-fmp-latest-top20/` and versioned by the source zip `sha256` in its `MANIFEST.json`. Refresh the bucket with `npm run fmp:holdings:bucket -- --source <unzipped-drop> --sha <zip-sha256>`. This is a separate consumer/book from the person-pages task's PelosiTracker positions handoff (`src/lib/tracker/`); do not re-parse or re-wire that bundle here.

- `person-index-map.ts` (pure): per person derives the ticker set, the weight basis (annual holding value midpoint), and the resolved Solana leg per ticker in the fixed order **xStock → verified Backpack `.US` → unmapped** via the Solana catalog's `preferredToken`. Every mapped leg carries the exact catalog mint and its evidence; a mint is only ever the catalog's own, never guessed and never a lookalike/similar ticker (GOOG ≠ GOOGL). Unmapped is first-class: `coverage.unmappedByWeightBps` discloses the dropped share; weights renormalise across mapped legs only, never silently around an unmapped leg. Transaction-derived books (`bookSource: txn-derived`) are activity, never weights — they stay `BLOCKED`. An annual book with no ticker rows is a separately-recorded gap (`no-ticker-holdings-in-annual-book`).
- `pool-evidence.ts`: pluggable per-mint Raydium pool source. `map-top20-index-vaults.mts` now adopts the landed `raydium-pools-mainnet` snapshot via `poolSourceFromReadiness(poolReadiness, meta)`; `PENDING_POOL_SOURCE` remains only for tests/fixtures. Never stand up a second pool registry. `raydium-pools-mainnet.ts` also owns the freshness guard: `snapshotFreshness`/`assertFreshPoolSnapshot` (pure, injected clock; 24h floor) fail closed on a stale snapshot so pool evidence is never used as if fresher than observed. Refresh with `npm run raydium:snapshot` (its candidate set now includes every FMP-annual mapped leg, not just tracker top holdings).
- `person-vault-init.ts`: builds the vault-init input (name/symbol, 25 bps in / 0 out host fees, start price, per-leg Raydium oracle token inputs guarded by `assertRaydiumOnlyToken`) from the pool-ready legs. **The native leg cap (100) is disclosed, never truncated: requesting more mapped legs than the cap throws** (`assertNativeTokenCap`). Fewer than two pool-ready legs throws; pool-excluded legs are recorded.
- `vault-definition-store.ts` + `supabase/migrations/202609160001_insiderindex_vault_definitions.sql`: **the keeper's target/eligibility source of truth is the DB record**, not local files. Definitions are upserted through the owner RPC (updated in place, versioned by hash + source sha256; a live `vault_address`/`share_mint` and last rebalance survive a refresh). `keeperTargets`/`vaultDriftFromRecord` hand the persisted vault legs straight to the shared `kakuSanDrift` eligibility math — no re-derivation in the keeper.
- **DB-driven keeper, operable by index id:** `keeper-tick.ts` + `scripts/insiderindex-keeper-tick.mts` (`npm run keeper:index`) run one tick for `--index <id>`, reading vault address, share mint, legs, target weight bps, cap, keeper and fee parameters from the definition row — no `--vault`/`--share-mint`, no hardcoded basket, so all four real vaults share one shape. **Dry run is the default** (loads no key, broadcasts nothing, prints current vs. target weights, drift and intended trades, records `mode:"dry-run"` and never a rebalance). `--execute --keypair PATH` needs the explicit flag AND the same shared eligibility rule; not-eligible does nothing and says so; force-rebalance is refused; a leg with no tradable pool is refused, never re-weighted around. The keypair stays a file-path argument (never an env var, refused inside the app tree, refused when it equals the deployer/host/strategy or a different named keeper). Every tick writes back through `recordRebalanceOutcome` → RPC `record_insiderindex_vault_rebalance` (`supabase/migrations/202609180001_insiderindex_vault_rebalance_record.sql`) so `last_rebalance_at`/`last_rebalance_result` are one source of truth. Operator runbook: [`docs/insiderindex-keeper-tick.md`](../../../docs/insiderindex-keeper-tick.md); tests `tests/insiderindex-keeper-tick.test.mts`.
- `thematic-index-map.ts`: the **10 constructed multi-member thematic research baskets** (`src/lib/thematic/`) become first-class vault candidates through the SAME `buildWeightedIndexDefinition` core — identical catalog resolution, renormalised target weights, Raydium pool-readiness, native leg cap and deposit gate; no forked path. A thematic definition is truthfully `kind: "thematic"` (person-book counters zeroed, member roster + `basis: insiderindex-thematic` recorded, no bioguide), so it never reads as a person index. `deriveAllThematicIndexes(catalog, poolSource)` mirrors `deriveAllPersonIndexes` and consumes the same live pool source, so thematic tradable coverage is real, not a placeholder.
- **Deposit gate (per-vault, closed by default):** `depositGate` in `person-index-map.ts` drives `depositsEnabled`/`depositReason` from tradable coverage, NOT creation. A deposit opens only when every mapped leg has an observed tradable pool (`poolReadyOfMappedBps === 10000`); otherwise weight would strand on a leg that cannot be rebalanced or exited to USDC. `vault-definition-store.ts` persists `deposits.{enabled,reason,releaseGated,effectiveEnabled}` where `effectiveEnabled = depositsEnabled && VAULT_RELEASE.publicFundsEnabled` — the release flag stays authoritative on top. Migration `202609170001` adds the `kind` / `deposits_enabled` / `deposit_reason` columns and a server-side guard (deposits cannot be enabled without a CREATABLE, fully pool-ready composition), and fixes the `read_insiderindex_vault_definition` GROUP-BY error in `202609160001` (single-row read is a plain projection, no `count(*)`).
- Dry-run only: `npm run indexes:map:top20` derives all 20 published indexes (10 person + 10 thematic) plus the 10 non-publishable people against the fresh pool snapshot, writes `evidence/vaults/top20-index-map-dry-run.{json,md}` and upserts to the DB only with `--publish`. The report distinguishes **catalog coverage** (`mappableByWeightBps`: book weight that maps to a mint) from **tradable coverage** (`tradableByWeightBps`: book weight behind a real, tradable pool — same whole-book basis, the number the create decision rests on), gives each index one verdict (`creatable now` / `creatable but below publish bar` / `creatable — would misrepresent (do not publish)` / `wait-pool-evidence` / `blocked`) and separately its deposit-ready state with reason, ranks the thematic baskets by tradable coverage, and totals per-vault estimated SOL into a **total SOL to create all 20**. A not-ready (thin/absent-pool) leg never enters tradable coverage; weight is never re-weighted around a missing leg. No signing, no broadcast, no keeper key. `tests/person-index-map.test.mts`, `tests/thematic-vault-defs.test.mts`, `tests/insiderindex-bucket.test.mts` and `tests/pool-snapshot-freshness.test.mts` cover resolution order, lookalike rejection, cap-exceeded throwing, txn-derived-never-weighted, bps integrity, pool gating, tradable-coverage exclusion of not-ready legs, thematic-never-person-provenance, deposits-default-closed, snapshot freshness, and source-bucket integrity.
